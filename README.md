# Plotskart

Plot inventory, sales, payments and reminders for real-estate owners and their sales teams.
One codebase runs as a website (desktop and phone browsers) and as Android and iOS apps through Capacitor.

- **Owner** sees everything: all projects, finance and profit/loss per project, team commissions.
- **Sales team** books and sells plots, records payments, changes prices, sends reminders.
- **Brokers** see layouts and can book plots. They only see reminders for plots they handled.

Every change goes through a database function that checks the person's role, records the plot history,
notifies the rest of the team (live in the app and by push notification) and, where needed,
queues a WhatsApp + SMS message to the customer.

## What's in here

| Path | What it is |
| --- | --- |
| `src/` | React app (Vite + TypeScript) |
| `src/lib/layouts.ts` | Plot layout builders: the traced Jatwada layout and a regular-blocks generator |
| `supabase/migrations/` | Database: tables, access rules, plot actions, daily reminder job |
| `supabase/functions/deliver/` | Sends push notifications (Firebase) and customer WhatsApp/SMS |
| `android/` | Native Android project (generated by Capacitor) |
| `capacitor.config.ts` | App id and name for the stores |

## 1. Supabase (backend)

1. Create a project at [supabase.com](https://supabase.com). Pick the Mumbai region for Indian users.
2. Install the Supabase CLI, then from this folder:
   ```bash
   supabase link --project-ref YOUR-PROJECT-REF
   ```
   ```bash
   supabase db push
   ```
   This creates the tables, access rules, live sync and the 8 am daily reminder job.
3. **Sign-in email:** Dashboard → Authentication → Email Templates → *Magic Link*. Make the email show the
   code by including `{{ .Token }}` in the body, for example: `Your Plotskart sign-in code is {{ .Token }}`.
   For real users, set up your own SMTP sender under Authentication → SMTP, because Supabase's built-in
   mailer is rate-limited.
4. Copy `.env.example` to `.env` and fill in the project URL and anon key from Project Settings → API.
5. Run the app:
   ```bash
   npm install
   ```
   ```bash
   npm run dev
   ```
   Sign in with your email. The first sign-in asks for your company name and makes you the owner.
   Use **Projects → Add a project** to create a layout (choose *Jatwada layout (traced)* to load the sample drawing).

### Delivery of push and customer messages

The database hands each new notification and customer message to the `deliver` edge function.

1. Deploy it:
   ```bash
   supabase functions deploy deliver --no-verify-jwt
   ```
2. Store its address and a shared secret in Vault (SQL editor). Use any long random string for the secret:
   ```sql
   select vault.create_secret('https://YOUR-PROJECT-REF.supabase.co/functions/v1/deliver', 'deliver_url');
   select vault.create_secret('YOUR-LONG-RANDOM-SECRET', 'deliver_secret');
   ```
3. Copy `supabase/functions/.env.example` to `supabase/functions/.env`, fill it in (same secret as above), then:
   ```bash
   supabase secrets set --env-file supabase/functions/.env
   ```

Providers you have not configured are skipped. The message is still logged, and the app shows its status
under Reminders → *Messages sent to customers*.

## 2. Push notifications (Firebase)

1. Create a Firebase project and add an **Android app** with the same id as `appId` in `capacitor.config.ts`.
   Download `google-services.json` into `android/app/`.
2. Add an **iOS app** with the same bundle id. Download `GoogleService-Info.plist` into `ios/App/App/`.
   Upload an APNs authentication key under Project settings → Cloud Messaging.
3. Project settings → Service accounts → *Generate new private key*. Paste the JSON on one line as
   `FCM_SERVICE_ACCOUNT` in `supabase/functions/.env`, then set the secrets again.

The app id is `in.plotskart.app` (in `capacitor.config.ts` and `android/app/build.gradle`). It cannot change
after the first store upload.

## 3. WhatsApp and SMS to customers

All WhatsApp messages go out from **one Plotskart number** through the Meta WhatsApp Cloud API, using approved
templates whose last variable is the developer's name. **WHATSAPP_SETUP.md** has the Meta steps and the exact template
texts. In the code:

- **Consent**: the booking and sale forms have a "Customer agreed to … WhatsApp" tick box (`plots.buyer_whatsapp`,
  changeable later with `set_buyer_whatsapp`). Buyers who didn't agree get SMS only; their WhatsApp status shows
  "no consent". Cancelling a booking clears the consent.
- **Sending**: `deliver` (`supabase/functions/deliver/`) sends only messages the database marked `queued`, normalises
  Indian and UAE numbers (`_shared/whatsapp.ts`) and stores Meta's message id.
- **Receipts and STOP**: `whatsapp-webhook` checks Meta's signature (`WHATSAPP_APP_SECRET`), records sent, delivered,
  read or failed, and switches WhatsApp off for a buyer who replies STOP.
- **Team alerts** (`team_messages`): everyone turns them on for themselves under **Reminders → My WhatsApp alerts**
  (`set_my_whatsapp`). Owner, sales and the plot's handler get bookings, sales and payments (a trigger on
  `plot_events`) and overdue buyers (with the daily payment reminder); never the person who made the change.
- **Owner daily summary**: `run_owner_summaries()` at 08:05 India time (pg_cron `plotskart-owner-summary`), once a day,
  only on days with something due, a registration or an overdue buyer.
- Secrets: `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`
  (optional `WHATSAPP_LANGUAGE`, default `en`).
- Tests: `npm run test:db` (consent, template variables, opt-out) and `npm run test:fn` (numbers, signatures, webhook parsing).

**SMS** (MSG91): Indian SMS needs DLT-registered templates. Create one Flow template per type with
`##var1##`, `##var2##`, … in the same order as the WhatsApp variables. Set `MSG91_AUTH_KEY` and the three
`MSG91_TEMPLATE_*` ids.

## Layouts from a photo or PDF

**Projects → Add a project → Photo or PDF of layout.** The picture is resized in the browser and stored in the
private `layouts` bucket. Then the `read-layout` edge function asks Claude (`claude-opus-5-5`) for every plot's number,
position, size and facing. The owner checks the result in the layout editor before saving.
**Edit layout** on a project opens the same editor for existing projects (`save_layout` keeps customers and payments).

Setup: add the secret `ANTHROPIC_API_KEY` (from console.anthropic.com) under Supabase → Edge Functions → Secrets.
Without it, the picture still uploads and plots can be placed by hand. Deploy changes with:
```bash
npx supabase functions deploy read-layout --use-api
```

## Apartment projects

**Projects → Add a project → Set up an apartment project.** The owner enters the pricing (base rate per saleable sq ft,
floor rise per sq ft for each floor above a chosen floor, car park price, GST shown to buyers, RERA number), the unit
types (carpet, built-up and saleable area), one **typical floor** (flat numbers, type, facing, car parks, preferred
location charge) and the towers with their number of floors. `create_apartment_project` repeats the typical floor
on every floor of every tower; flats are numbered `<tower>-<floor><flat>`, e.g. `A-1203`, ground floor `A-G01`.

- A flat is a row in `plots` with `tower_id`, `floor`, `unit_type_id`, `plc_paise` and `parking_slots`, so booking,
  sale, payments, instalments, receipts, reminders, WhatsApp, commissions and finance work exactly as for plots.
- Price (`_value()` in the database, `priceParts()` in the app) = saleable area × rate + floor rise + preferred location
  charge + car parks. GST is shown on top. New money columns are paise (`bigint`).
- The project page shows a **stacking plan** (each tower top floor first, flats colour-coded), a flat list, a
  by-tower summary and the unit types with their **floor plans** (owner uploads a photo or PDF; `set_unit_type_plan`).
- The owner changes a single flat's type, car parks or preferred location charge from the flat (`update_unit`).
- Apartment projects can't be edited as a layout drawing (`save_layout` refuses them).
- The demo company gets an apartment project, Skyline Residency, alongside the two plot layouts.

## Money features

- **Roles:** owner, sales, broker and **accountant**. The accountant handles payments, bank & cash, expenses, salaries and reports, but can't book, sell, change prices or manage the team.
- **Ledger:** every rupee in or out is a dated `ledger` row tied to an account. Customer payments, expenses, commissions, salaries, transfers and asset purchases write to it automatically, so account balances are always opening balance + ledger.
- **Instalments:** a plot's `due_date` is always the first instalment not yet covered by payments.
- **Receipts:** numbered per company automatically.
- **Documents:** stored in the private `documents` bucket.
- **Reports:** for any period, using the Indian financial year (April–March).

## Plans and limits

Pricing on plotskart.in (30 Oct 2026) is enforced in the database by `20261104000000_plans_and_limits.sql`,
so the web app and the phone apps follow it without an app update.

| Plan | Owners | Team logins | Projects | AI layout reads | Customer + team WhatsApp/SMS |
| --- | --- | --- | --- | --- | --- |
| `free` | 1 | 0 | 2 | 1 per project (2 in total) | none; app and push alerts only |
| `team` | 1 | 5 | 5 | 5 a month | 1,000 a month |
| `business` | 2 | 15 | 10 | 10 a month | 2,500 a month |

- New companies start on `free`. Companies that existed before the migration were put on `business`.
- Past the monthly allowance, top-up credits are used (`extra_ai_reads` at ₹99, `extra_messages` at ₹1);
  after that AI reads are refused and messages are logged as `monthly limit reached` (never sent).
  In-app and push notifications are never limited. Demo companies skip plan limits.
- After a customer pays, change their plan or add top-ups from the SQL editor as the service role:
  ```sql
  select admin_set_plan('<company id>', 'team');
  select admin_add_credits('<company id>', p_ai_reads => 5, p_messages => 500);
  ```
- The owner's current plan and this month's usage: `select my_plan();` (owner only).

## Demo mode

`https://demo.plotskart.in/?demo` gives each visitor a private sample company (owner, two
salespeople, a broker, two projects with sales history) with no sign-in. The `demo-start` and `demo-switch`
edge functions handle sign-in. Each browser tab has its own sign-in, so "Open another person in a new tab"
shows live sync between roles. The browser keeps a resume key, so a returning visitor (or a new tab)
reopens their own demo company instead of starting another; **Restart demo** starts a fresh one.
New demo companies are limited to 30 per visitor address and 1,000 in total per day (`demo_allow_start`).
Demo companies never send WhatsApp/SMS or push, get 3 automatic layout reads,
and are deleted after 3 days (pg_cron `plotskart-demo-cleanup`).

```bash

```
This runs the migration in an in-memory Postgres (PGlite) with small stand-ins for Supabase's auth, cron,
net and vault. It then checks the booking → sale → payment → reminder flow and the access rules for each role.

## How reminders work

- `run_daily_reminders()` runs at 08:00 India time (pg_cron job `plotskart-daily-reminders`).
- **Registration:** alerts start `reg_days` before the registration date (default 2) and go out once per date.
- **Payment:** reminders start `pay_days` before the balance due date (default 3), then repeat daily while
  overdue, for up to 30 days.
- Each reminder sends an app notification to the owner, the sales team and whoever handled the plot,
  plus WhatsApp + SMS to the customer. The owner changes the timing on the Reminders page.
- The sales team can also send a reminder by hand with **Send now**.
